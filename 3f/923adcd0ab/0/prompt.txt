Build a minimal, reliable software factory in this repository using the currently installed Pi and pi-subagents APIs.

   This is an implementation task. Keep the parent Pi session as the orchestrator, use one writer at a time, and run fresh-context reviewers after
 implementation.

   ## Goal

   Add a reusable `/factory <task>` command that launches an asynchronous, bounded software-delivery workflow:

   scout → plan → implement → deterministic checks → parallel review → optional fix → final checks

   The factory should provide reliable outcome-oriented software delivery. It should not attempt to recreate Nika’s language, static proof system,
 hash-chained traces, or general-purpose workflow engine.

   ## Architecture

   Prefer a thin Pi extension that calls pi-subagents through its documented in-process RPC API.

   The extension should:

   - register `/factory <task>`
   - validate project trust and repository state before launch
   - construct one fixed `workflowScript` with the human-provided task safely JSON-encoded
   - launch it asynchronously through `subagents:rpc:v1:request`
   - correlate RPC replies by request ID
   - report the workflow run ID and mission ID
   - expose `/factory-status` for the latest factory run
   - avoid implementing its own child runner, process supervisor, scheduler, worktree manager, or transcript store

   Use pi-subagents as the owner of execution, lifecycle, missions, artifacts, status, resume, and Herdr integration.

   Herdr is observational only. Do not orchestrate the workflow by sending terminal keystrokes or scraping panes.

   ## Factory workflow

   Implement these phases with stable workflow keys:

   ### 1. Scout

   Launch a fresh-context `scout`.

   Require a structured output schema containing:

   - summary
   - relevant files
   - constraints
   - likely risks
   - recommended implementation seam
   - existing validation commands found in trusted repository configuration

   The scout must not edit files.

   ### 2. Plan

   Use a read-only planner agent if one already exists. Otherwise add the smallest packaged `planner` agent needed for this workflow.

   Require structured output containing:

   - implementation steps
   - files expected to change
   - non-goals
   - validation plan
   - decisions requiring human approval

   Do not proceed when the plan contains an unresolved human-owned decision.

   ### 3. Implementation

   Launch exactly one `worker` as the sole writer in the current repository/worktree.

   Pass only the validated scout and plan fields, plus the original human task.

   Require a checked acceptance handoff containing:

   - changed files
   - implementation summary
   - commands run and exit codes
   - tests added or updated
   - residual risks
   - work left undone
   - decisions requiring approval

   Do not commit, push, merge, publish, deploy, or release.

   ### 4. Deterministic checks

   Run trusted, repository-owned validation commands through `runs.host`, not through another agent.

   Commands must come from explicit human-authored factory configuration or existing canonical project scripts. Never execute a shell command proposed
 only by an agent output.

   If no trustworthy validation commands exist, fail with an actionable message instead of inventing one.

   ### 5. Parallel review

   Launch fresh-context read-only reviewers in parallel:

   - correctness and regressions
   - tests and validation quality
   - simplicity and maintainability

   Require structured reviewer output with:

   - verdict: `ok`, `fix`, or `blocked`
   - findings with priority, evidence, file, and line
   - remaining risks

   Reviewer prose alone must not control branching; branch only on the structured verdict.

   ### 6. Fix pass

   If any reviewer returns `fix`, launch one worker to apply the parent-synthesized, in-scope fixes.

   Do not apply `blocked` findings that require a product, architecture, security, or scope decision. Record those as decisions requiring human input.

   Cap the first version at one fix pass. Do not create an unbounded review loop.

   ### 7. Final verification

   Rerun the trusted deterministic checks.

   Return a concise result containing:

   - workflow and mission IDs
   - final verdict
   - changed files
   - validation commands and results
   - reviewer disposition
   - residual risks
   - artifact references
   - explicit statement that no commit, push, deploy, or release occurred

   ## Reliability requirements

   - Use `workflowScript`, `runs.run`, `runs.all`, and `runs.host`.
   - Use fresh context for scout, planner, and reviewers.
   - Use one writer at a time.
   - Use stable keys for every stage.
   - Use `outputSchema` for every machine-consumed agent result.
   - Validate the generated workflow before spawning children.
   - Use a default durable mission and bounded mission state.
   - Preserve run, child, output, and artifact references needed for recovery.
   - Use explicit timeouts and sensible concurrency bounds.
   - Treat missing output, malformed structured output, failed checks, and inconclusive process state as failure or needs-attention—not success.
   - Do not claim exactly-once execution, deterministic model output, tamper-evident traces, or Nika-equivalent security.
   - Do not blindly retry side-effectful operations.
   - Assume the current repository is already the intended isolated worktree. Refuse a dirty baseline unless an explicit configuration option allows
 it.

Launch parallel reviewers for an adversarial review of the current work.

Use fresh context, not forked context, unless I explicitly ask for forked context. Reviewers should inspect the repository, relevant instructions, and current diff directly from files and commands. Do not rely on the main conversation history.

Give each reviewer a distinct angle. Generate the angles dynamically from the user's intent, the plan, the implemented code, and the current diff. If I specify angles, use mine. Otherwise, choose the highest-value review angles for this specific work.

These are examples, not fixed defaults:

1. Correctness and regressions
   Check whether the change satisfies the request, preserves existing behavior, handles edge cases, and avoids hidden runtime failures.

2. Tests and validation
   Check whether tests or validation were added at the right layer, whether assertions are meaningful, and whether the chosen verification commands are enough.

3. Simplicity and maintainability
   Check for unnecessary complexity, duplicate structure, single-use wrappers, brittle abstractions, confusing names, verbosity, and cleanup that is clearly worth doing.

Choose or adapt angles when the work calls for it:
- TypeScript-heavy changes: include type safety, source-of-truth types, casts, and error-boundary discipline.
- UI-heavy changes: include UX, accessibility, copy, and visual quality.
- Security-sensitive changes: include unsafe input/output handling, auth boundaries, privacy, and data exposure.
- Docs-heavy changes: include clarity, accuracy, completeness, reader flow, and non-robotic prose.
- Large multi-file changes: consider a fourth reviewer for structural friction, module boundaries, and testability.

Prefer three strong reviewers over many vague reviewers.

Give every reviewer a specific task prompt naming its angle. Ask reviewers to return concise, evidence-backed findings with file/line references and suggested fixes. Filter on evidence, not severity: a finding must be concrete, current, caused or made reachable by the target diff, and supported by source proof, a test or repro, or a contract contradiction. Label findings P0/P1/P2. P0 blocks merge. P1 should be fixed before release. P2 is report-only. End each review with `Merge verdict: BLOCK`, `Merge verdict: OK`, or `Merge verdict: OK with notes`. If nothing qualifies, ask the reviewer to say exactly `No issues found.` The response should be review feedback, not a context summary. Reviewers must not edit files unless I explicitly ask for a writer pass.

Do not default first-pass reviews to `blockers only`. That phrase is valid only for final pre-merge re-checks after P1/P2 findings are already inventoried, or for explicit emergency hotfix lanes where non-blocking findings are intentionally deferred.

For a targeted follow-up review, ask only whether the named finding was resolved, whether the fix introduced a new defect in the fix blast radius, and whether prior P1/P2 notes still stand. For bot or PR-comment triage, classify each comment as VALID, STALE, INVALID, or OUT-OF-POLICY against current HEAD, then assign P0/P1/P2 only to VALID comments.

While reviewers run, do your own narrow inspection if useful. After they return, synthesize the feedback into:
- fixes worth doing now
- optional improvements
- feedback to ignore or defer, with a short reason

Do not blindly apply every reviewer suggestion.

Autofix mode: if the invocation contains the exact word `autofix`, treat it as workflow control, not review scope. Remove it before deciding the review target. After synthesis, apply only fixes worth doing now, validate, and summarize. Do not apply optional improvements unless explicitly requested. If there are no fixes worth doing now, do not edit.

Without autofix mode, ask before applying fixes unless I already told you to address review feedback. When you ask, end with a compact numbered menu so I can respond with a number. Use wording suited to the findings, but include these choices when applicable:

```text
Reply with [1], [2], or further instructions:
[1] Apply only the fixes worth doing now.
[2] Apply the fixes worth doing now plus optional improvements.
```

If the invocation provides a URL, issue link, file path, plan path, or freeform focus, treat it as the primary review scope. Read or fetch that target before assigning reviewer angles, and pass the target explicitly into each reviewer task.
