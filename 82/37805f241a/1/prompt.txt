## Safety / cache policies for integration docs

- Public HTTP(S), standard ports 80/443, no URL credentials, cookies/auth forwarding, browser, PDF, or hosted extraction.
- DNS responses must all be public vetted literal addresses; the actual Node HTTP(S) request receives a custom pinned lookup, no second DNS lookup, no pooled agent, and no proxy routing. HTTPS explicitly enables certificate verification and preserves the original DNS hostname for SNI/identity checks.

# Cache contention fix — P2 full-host payload rescanning on every insert

Worker: cache-accounting seam only. Files changed relative to the CURRENT DIRTY SNAPSHOT baseline (root main HEAD 94ef96c + pre-existing untracked perplexity work): **only** `extensions/perplexity/evidence-store.ts`, `tests/perplexity/evidence-store.test.ts` (1 line), and new `tests/perplexity/cache-quota.test.ts`. No other file touched; nothing staged/committed; no README/package/lock/profile edits; all fixtures in /tmp; the real default evidence cache was never read.

## What was wrong

`planEviction` read, parsed, schema-validated and SHA-256-hashed **every host snapshot record** while holding the single host writer lock, on **every** insert. With the allowed cache populated (e.g. 16 scopes × 128 × 240 KiB ≈ 481 MiB), independent healthy writers expired the 10 s lock-wait deadline before their turn → `cache-busy` failures (reviewer reproduced: 6 of 12 concurrent writes failed). Fix had to avoid merely increasing timeouts.

## What was implemented (evidence-store.ts only; `cache-index.ts` not needed)

Compact **schema-versioned quota metadata** under the existing host lock, replacing per-write payload rescans:

- **New root-private internal file** `<root>/.evidence-quota-v1.json` (`QUOTA_METADATA_NAME`), never inside a scope directory, so scope record-listing semantics are unchanged. Written atomically (temp + fsync + rename) at 0600 under the same `locked()` host writer lock — correctness is on-disk, never in-process memory; independent processes/resume honor quotas (tested with fresh instances).
- **Schema v1 index entry**: `{ id (uuid), scope (hex64 dir), bytes, createdAt, expiresAt }`, `additionalProperties: false`, `maxItems: METADATA_MAX_RECORDS` (8192). **Bounded**: `METADATA_MAX_RECORDS = 8192`, `METADATA_MAX_BYTES = 2 MiB`; loads/writes beyond bounds fail loudly (`invalid-cache-schema` / `cache-size`). At default limits (2048 records) overhead is ≤ ~400 KiB worst case (~180 B/entry).
- **Planning (`planEviction`/`evict`)** loads metadata and does **stat-level** size/identity checks (`lstat` per indexed record + `readdir` per scope for identity/divergence). **No record payload is reread or rehashed during planning.** Quota accounting uses actual `lstat` sizes, so stale byte metadata cannot bypass quotas. Eviction semantics unchanged: TTL/count/bytes oldest-first, same own-scope/host limits, same victim ordering.
- **Actual record reads (`get`)** are unchanged: full schema, scope-id, id-match and SHA-256 content-hash validation on every read; no refetch.
- **Legacy migration (explicit, once, tested)**: missing metadata file (`ENOENT`) triggers `rebuildIndex` — a full read+validate of every existing record (the same validation the old planner did), indexing only what is already on disk: **no refetch, no new ids**. Old pre-metadata writers (which never write metadata) simply re-trigger this rebuild; safe, just slower.
- **Divergence handling (all tested)**:
  - Metadata-listed file missing (`ENOENT`) → stale entry dropped (crash between eviction unlink and metadata write); non-ENOENT IO failures are never swallowed.
  - Record on disk absent from metadata (old writer, or crash between record commit and metadata update) → one explicit full rebuild, then planning proceeds.
  - Metadata-listed file size ≠ actual size (records are immutable ⇒ tampering/corruption) → loud `invalid-cache-schema`; no quota bypass from stale metadata.
  - Handled metadata-write failure → the just-written record is removed (best-effort; residual divergence is recoverable by the same rebuild path) and the **original error** is rethrown; the pre-existing cancellation-promise structure is preserved exactly (commit boundary, bounded cleanup after mutation begins, cancellation reported after lock release — existing abort tests pass unchanged except one assertion adapted to the new `planEviction` return shape, invariant preserved).
- **Corrupt/foreign-version metadata** (unreadable JSON, schema mismatch, `schemaVersion ≠ 1`) fails loudly; reads stay available; removing the corrupt file makes the next write rebuild (tested).
- **No stale lock deletion**: `locked()` crashed-lock fail-closed behavior untouched.
- **Observability seam** for the required structural test: exported `recordReadInstrumentation { reads, bytes }` counting full reads through `readPrivate` — lets tests prove a warmed insert reads **only** the metadata file (1 read, <8 KiB) while seeded payloads are ~96 KiB each, and that an actual read does exactly one full payload read. Instrumentation deltas also prove the legacy rebuild really scans (7 reads for 7 records).

No `cache-index.ts` was added — the index is ~100 lines tightly coupled to `evidence-store` internals; a second module would widen the seam without benefit. No host/Pi API assumptions were made (module uses only node:fs/crypto/typebox); installed Pi 1.0.0 docs root was checked and confirms this seam touches no extension/TUI/package host surface.

## Finding 1 — legal max-size frame failed depending on delimiter split location

**Root cause (baseline `perplexity.ts:389`):** the pending-frame check `pending.length > maxBody` counted an incomplete trailing delimiter prefix (e.g. the first `\r` of a split `\r\n\r\n`) as frame payload, so a 2 MiB-legal comment frame succeeded coalesced but failed with `Perplexity SSE frame limit exceeded` when cut inside its delimiter.

**Fix (in `sse-framer.ts`):**
- The pending frame cap subtracts ONLY the longest ACTUAL trailing partial delimiter prefix (≤ 3 bytes; the only proper prefixes of `\r\n\r\n|\n\n|\r\r` are `\r`, `\n`, `\r\n`, `\r\n\r`), evaluated over the merged tail (last ≤3 bytes of the retained frame + last ≤3 of the chunk).
- If later bytes disprove the prefix, the scan reclassifies them as payload and the cap is re-checked immediately — no fixed `max+3` relaxation can accept an oversize frame. Proof of no false accept: any future delimiter must start at position ≥ `end − partial`, so `frameBytes − partial` is a lower bound on the eventual frame size; disproven bytes are caught by the next scan's recheck; dispatch and the EOF flush enforce the exact `Buffer.byteLength(frame) > maxBody` cap (dispatch check unchanged in `perplexity.ts`).
- The pre-terminal TOTAL budget still counts ALL received prefix bytes exactly once — frames, complete delimiters, and undelimited pending bytes including a partial delimiter prefix (`charged` is incremented at append/discovery time; post-terminal suffix bytes inside a chunk are never seen, copied, or charged because scanning stops at the first frame whose callback reports the terminal).

**Delimiter split supported for any prefix:** LF, CRLF, CRCR delimiters, split at ANY byte, any number of fragments, including a delimiter split across 3+ chunks (e.g. `"\r"|"\r"` or `"\r\n"|"\r"` straddles resolved via a ≤6-byte boundary probe of the retained frame's last ≤3 scanned bytes + chunk head).

## Finding 2 — quadratic pending copies + event-loop/deadline starvation

**Root cause (baseline `perplexity.ts:365–383`):** every fragment merged the whole growing pending buffer (`new Uint8Array` + two `set`) and `pending.slice(start)` copied again per chunk; reads of immediately-ready fragments formed a promise-microtask loop so the `setTimeout` deadline never fired (measured 9 399 ms for a 2 096 922-byte stream in 16-byte fragments with a 10 ms injected deadline; independent 10 ms timer never fired).

**Fix:**
- **Amortized-linear storage (`sse-framer.ts`):** chunks are scanned IN PLACE and dispatched frames are handed over as views with no copy; only the undelimited in-progress frame is retained in a single geometrically grown buffer (start/end/scanned indices; `copyWithin` compaction of dispatched bytes before growth). Each received byte is appended at most O(1) amortized times; no full copy when `start === 0` (growth instead of compaction); oversize frames/oversized chunks are rejected BEFORE copying via pre-copy candidate checks (`frameBytes` computed from indices); post-terminal tail bytes in a chunk are never copied (scan stops at the terminal frame).
- **No repeated rescans:** `scanned` maintains "no delimiter starts in `[start, scanned)`"; only the last ≤3 bytes (max partial delimiter prefix) are ever rescanned.
- **Event-loop yielding:** the stream read loop yields via `setImmediate` every 64 reads or ≥ 262 144 processed bytes, so deadline/abort macrotasks fire during immediately-ready fragment reads.
- **Absolute monotonic deadline shared with Search/Agent budgets:** `withTransport` now computes `budgetMs = Math.min(deps.deadlineMs ?? deadlineMs, deadlineMs)` once, an absolute `deadline = performance.now() + budgetMs` (monotonic clock) shared by the unchanged `setTimeout` timer and the consume loop (passed as a new 4th `consume` parameter — internal signature only; Search/Agent consumes ignore it). The stream loop checks `signal.throwIfAborted()` then `performance.now() >= deadline` every iteration and before EVERY success return (including the early-terminal return), so a consume finishing after the deadline can never report success. Caller abort still maps to `AbortError` (throwIfAborted runs first; `withTransport` catch maps `signal.aborted` to AbortError); pre-terminal expiry rejects with the same `"Perplexity request deadline exceeded"` message and the `finally` still cancels + releases the reader; callback errors are not swallowed (they propagate through `feed` untouched).

**Preserved policies:** raw-UTF-8 fatal per-frame decode, first-authoritative-completion early stop, source-ID reconciliation, EOF-without-completion failure, exact body/frame limits and their error strings, "transport interrupted" mapping, reader cancel/release. HTTP/body/cancellation behavior of the shared transport is untouched except the additive `deadline` parameter.

## Exact recovery cause + temp cleanup scope (for the integrator)

- Cause: after a quota temporary is opened/written/fsynced at the host root, if the actual `rename` (and the temporary's own cleanup `unlink`) fails — e.g. the root lost write permission (EACCES), or other inner FS faults — the handled failure still rolls back the incoming record from its still-writable scope, but the root temporary is stranded. `rebuildIndex` collected such temporaries only on the cold (no-index/rebuild) path; the warm root scan skipped every non-scope name, so the next warm insert left the `.tmp-quota-<uuid>` file permanently. This contradicted `extensions/perplexity/README.md`'s "next write removes owned stale atomic-write temporary files" promise.
- Fix scope: warm root scan now adds validated root `.tmp-quota-<uuid>` names to planned removals under the same host lock, cleaned after the cancellation commit boundary; cold rebuild path already cleaned them and now dedups against the warm collection.
- README needs: none new. The existing README sentence already promises this cleanup; the code now honors it on the warm path. No README edit was made (integration owns sync); no wording change required for this fix.
